## 结果与契约

管理 client 新增可选 `cacheScope: { backend, identity }`，两个字段均为非秘密逻辑 ID。client 暴露不可变的 `cacheScope` tuple，所有管理 hooks、11 个 server prefetch helper、query key、mutation invalidation、充值审核的 optimistic update / rollback 均以它为前缀。高级调用方使用 `ledgerKeys.balances(client.cacheScope, holder)`、`ledgerKeys.all(client.cacheScope)`；旧的无 scope key API 会编译失败。

未配置显式 scope 时，每个 client 只生成一次随机实例 ID。provider 对实际请求参数 `baseUrl`、`apiKey`、`fetch` 引用进行 memo；这些可观察配置变化会产生新实例和 scope。client 对传入配置做快照，避免调用方事后修改对象，让旧 cache namespace 的请求转向另一个 backend。scope 不包含 URL 或凭证，且已知 `apiKey` 出现在显式 scope 中时会直接拒绝，不回显秘密值。

显式 scope 是宿主对真实 backend / 身份 / 权限版本的声明。SSR 内网 URL 和浏览器 BFF URL 不同，但可显式共享相同逻辑 backend 与 identity。相反，即使 API key 改变，只要宿主继续提供相同显式 identity，SDK 就仍按共享身份处理，不声称能从 key 推断真实用户。隐藏 BFF cookie 的变化不可由 SDK 自动观测；宿主必须在登录、注销、切换账号/租户/权限边界时换 scope，或重挂并提供新的 QueryClient。测试与 README 均明确这一限制。

provider 按 scope 为其 context 子树设置 key，身份变化时重置本地表单、preview 和 mutation 状态。它拥有的 QueryClient 随子树更新；若宿主注入自己的 QueryClient，旧条目可能仍留在内存，但新 scope 不会读到。scope 是缓存隔离机制，不替代服务端授权，也不承诺自动清理宿主保留的旧数据。

## 延迟 mutation 的实际验证

所有直接 mutation 以及 `useLedgerMutation` 都设置 scoped `mutationKey`。核对当前安装的 TanStack Query 源码 `web/node_modules/@tanstack/query-core/src/mutationObserver.ts`：key 变化会 reset observer，避免将新 scope 的 callbacks 写入仍 pending 的旧 mutation。仅改 query key / invalidate prefix 而不固定这个生命周期，会让旧请求完成时调用新 scope 的闭包。

`test/hooks/scoped-mutations.test.tsx` 直接保持 hook 挂载并替换 client context，使用真实 QueryClient 和可控制完成时刻的 Promise，验证 post journal、reverse journal、metadata create 在 A 请求 pending 时切至 B，完成后只使 A 失效。approve/reject 的 A optimistic queue 修改、延迟失败 rollback 以及 invalidation 也只影响 A；B 的原数据和有效状态保持不变。通用幂等键 map 同时包含 scope 与 payload，保留同身份重试键，跨身份不复用。

`getDashboardCacheScope()` 先 `await cookies()` 进入请求动态边界，再读取新的逻辑 backend 配置。它使用现有 `verifySession` 核验 cookie 后，才把公开 expiry 映射为 `operator-session:<expiresAtMs>`。未登录、失效、过期或签名伪造使用 `anonymous`；关闭认证的开发模式使用独立 `development-open`。生产缺失密码时不会落入开发身份，既有 proxy/BFF 仍负责拒绝未授权访问。

token 原格式只有 expiry 和签名，同毫秒 mint 的 token 相同，因此也共用同一 cache identity。这是现有认证会话边界，不是逐次登录事件的唯一 nonce。没有把 raw token、签名/HMAC、API key、凭证摘要或内网 URL 写入 scope。有效 cookie 的公开 expiry 不是授权凭证。

## 配置迁移与动态渲染

生产环境新增必填 **`LEDGER_CACHE_BACKEND_ID`**，例如 `production-ledger-east`。它会出现在浏览器可见的 cache keys 中，必须是非秘密逻辑名称；更换实际 backend 时同步更换此值，不能使用 URL、API key 或 token。开发缺省值是 `local-ledger`。`.env.example` 与 SDK README 已说明迁移。

该配置只在请求期读取，不要求构建期部署凭证。验证时移除 `LEDGER_CACHE_BACKEND_ID`、`LEDGER_API_URL_INTERNAL`、`LEDGER_API_KEY`、`DASHBOARD_PASSWORD`、`DASHBOARD_SESSION_SECRET` 后执行 `next build` 成功。root layout 读取 cookie 会使其下页面（包括 login / not-found）动态渲染；最终路由表全部显示 `ƒ`，这是为准确传递请求身份而作的明确改变。没有 module-level QueryClient、共享 SSR 可变 cache 或凭证持久化。
