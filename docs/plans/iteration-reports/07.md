## 结果

新增唯一 `src/lib/parse-holder-input.ts`，两套 skin 的 Journals、Templates preview、Balances、Reconciliation、Snapshots 共 10 个页面入口复用它。holder 输入不再使用 `parseInt`，因此 `12abc` 不会指向 holder 12，`1.5` 不会指向 holder 1。余额 Search 和 Enter 调用同一个验证函数。

语法为 trim 后的 ASCII 十进制整数：允许一个前置负号、十进制前导零以及首尾空白；拒绝 `+12`、`12abc`、`1.5`、`1e3`、`0x10`、`0b10`、内部空白和非 ASCII 数字。错误提示说明仅允许十进制数字和可选前置负号；范围错误显示合法上下界。转换后必须满足 `Number.isSafeInteger`，合法 numeric SDK 范围是 `-9007199254740991` 到 `9007199254740991`。`9007199254740992` / `9007199254740993` 及对应负数都拒绝，不会把相邻大 ID 取整到同一个 holder。

同一个 parser 用上下文模式区分空值、零和 system holder：

| 模式 / 入口 | 空白 | 0 / -0 | 负 system holder |
|---|---|---|---|
| optional / Balances | 保持 `undefined`，仅由余额 UI 转为既有 0 哨兵 | 保持不查询 | 允许 |
| account / Reconciliation、Snapshots | 拒绝，提示 required | 拒绝，提示 non-zero | 允许 |
| user / Template Journal、Templates preview | 拒绝，提示 required | 拒绝，提示模板需正数 | 拒绝，提示模板需正数 |

模式依据真实实现：`core/template.go:127` 的 template render 要求正 user-side holder，system 行由取负派生；`server/handler_system.go:148` 的 account reconciliation 与 `:246` 的 snapshots 拒绝 0；`src/hooks/use-balances.ts` 用 0 表示 disabled，负数属于合法查询。没有把所有入口改为 positive-only，也没有放行 0 到真实 account endpoint。

无效输入在写 query state 或调用 mutation 之前给出对应 skin 的 toast，保留用户输入供修正，且不发错误 holder 请求。没有更改金额处理、UI 布局、client / hooks / types、缓存行为、依赖或 wire。`src/lib/utils/display.ts` 中下标字符转换使用的 `parseInt` 与 holder 无关，保留原样；扫描相关目录后只剩这一处 `parseInt`。

原始 journal JSON entries 继续使用既有 validator 和 Task 6 SDK 边界；本轮仅修复文本 holder 的解析与上下文语义，不扩大为整个 mutation schema 重写。
