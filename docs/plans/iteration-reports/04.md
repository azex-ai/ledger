# 第 4 轮：金额校验先于 tracing 展开

任务：Ledger20 Task 4 / bus #33，风险 T2。分支 `codex/ledger20-t04`；基线 `de583aa90a37a8ebf29b8a35db09d55fddcb012a`。

输入为审计 R4；输出为 Reserve / CreateBooking 的金额校验顺序修复、真实 PostgreSQL 与 OpenTelemetry 内存 exporter 回归。交由 root 做独立域评审、Codex 第二意见与串行集成；本报告保留验证证据。

## 改动与边界

`postgres.ReserverStore.Reserve` 与 `postgres.BookingStore.CreateBooking` 先运行 `input.Validate()`，只有成功后才执行 `Amount.String()` 构造 tracing 属性。校验失败仍创建、结束 span 并记录 error status / exception event，因此坏请求仍可观测；数据库操作留在校验成功之后。

所有属性继续通过 `ledgerotel.StartSpan`，保留 `PolicyMinimal` / `PolicyFull` 的现有过滤行为。没有直接调用 `span.SetAttributes`：该调用会绕过当前仅在 StartSpan 中实施的过滤，使默认隐去的金额重新进入 exporter。校验本身现在发生在 span 启动之前，失败 span 不包含 amount 属性。

同路径复核：Reserve 后续余额比较、错误格式化及 SQL 参数转换均位于校验后；CreateBooking 的 idempotency 匹配、币种精度检查与 SQL 转换也在校验后。Settle / SettlePartial 原已先校验再展开金额；Booking.Transition 在校验前不渲染金额，本轮不改它们。没有修改外部 signer、事务边界或 Capture 契约。

## 回归证据

`postgres/amount_magnitude_trace_test.go` 使用有限坏值 `1E13`、`1E-19` 和 `-1`，不执行旧版巨大指数。两种 tracing policy × 两个 store 组合验证：

- 坏输入返回 `ErrInvalidInput` 和 nil 结果；reservations、bookings、events、journals、journal_entries、balance_checkpoints、rollup_queue 行数不变，held amount 仍为零。
- 失败 span 仍结束并记录 Error 与 exception event；即使 PolicyFull 也没有未经校验的 amount 属性。
- 合法 `2.50` 请求仍成功，返回及实际 held amount 正确；PolicyFull 保留 `2.5` amount 属性，PolicyMinimal 继续隐藏 amount、account_holder 与 idempotency_key。

使用任务套件的 PostgreSQL 17，fixture 为每个 case 创建独立数据库，命令运行时 `DATABASE_URL` 指向临时服务。

- 修复前，`go test -race -timeout 3m ./postgres -run '^TestStores_AmountMagnitudeBeforeTraceFormatting$' -count=1`：PolicyFull 的 Reserve 与 CreateBooking 都因坏金额出现在属性中而失败，安全复现顺序缺陷。
- 修复后，`go test -race -timeout 10m ./postgres -run 'Magnitude|InvalidAmount|Reserve|Booking' -count=1`：PASS（39.781s），包括新回归与既有 Reserve / Booking 行为。
